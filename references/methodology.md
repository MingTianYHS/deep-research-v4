# 深度研究方法论：八阶段流程

**何时读取**：需要深入理解某一阶段的执行细节，或在 deep（深研）模式下执行提纲重构、批判回环与多角色红队时读取。日常研究按 `references/lead-playbook.md` 执行即可，本文件是方法层补充。

**用途**：定义从范围界定到交付的八个阶段，说明每个阶段的目标、活动、产出与质量门槛，并给出查询形态（direct / depth / breadth）× 验证强度（standard / deep）下的执行强度。

## 0. 两维研究路径

本技能不用单一档位，而是把两个维度组合成实际路径：

| 维度 | 取值 | 判定方法 |
| --- | --- | --- |
| 查询形态 | direct / depth / breadth | 看问题结构：单点事实、同一问题的多视角深挖、可拆成多个独立子问题 |
| 验证强度 | standard / deep | 默认 standard；关键决策、证据冲突、高风险领域或用户要求彻查时升为 deep |

| 实际路径 | 组合 | 适用场景 | 子代理 | 来源预算 |
| --- | --- | --- | --- | --- |
| 直查 | direct × standard | 单事实、定义、简单核对 | 1 个 | 3–5 |
| 标准研究 | depth / breadth × standard | 大多数研究请求 | 3 个 | 10–15 |
| 深研 | depth / breadth × deep | 关键决策、争议大、对比选型、尽调 | 3–5 个 | 20–30 |

各阶段的执行强度：

- **直查**：执行阶段 1、2、3（轻量）、5、8；跳过阶段 4.5、阶段 6 的多角色红队和阶段 7 的迭代补强。
- **标准研究**：执行阶段 1–8，但跳过阶段 4.5 的提纲动态重构；阶段 6 只做常规自检，不跑多角色红队。
- **深研**：执行阶段 1–8 全量；阶段 4.5 提纲动态重构、阶段 6 多角色红队与批判回环必须执行，来源预算更大。

## 阶段一：SCOPE 界定范围

**目标**：明确研究边界与成功标准。

**活动**：

1. 把问题拆成核心概念、关键实体及其关系。
2. 识别利益相关方与需要覆盖的视角。
3. 写明范围边界：哪些在范围内、哪些明确排除。
4. 定义成功标准：报告必须回答哪些问题、用什么证据判定回答成立。
5. 列出待验证的关键假设，并标明哪些假设会改变研究结论。

**产出**：写入 `研究计划.md` 的「范围与成功标准」一节。复杂问题先探索 2–3 种问题框架，再确定最终范围。

## 阶段二：PLAN 制定研究计划

**目标**：形成可执行的研究路径。

**活动**：

1. 区分一手来源与二手来源，优先一手来源。
2. 梳理知识依赖：哪些事实必须先确认，哪些结论依赖前序结果。
3. 设计查询式与变体：同义词、英文/中文表达、时间限定、站点限定。
4. 规划三角验证路径：每个关键结论准备 2 个以上独立来源簇。
5. 评估工作量与时间，确定子代理数量与批次。
6. 定义质量门槛：来源数量、来源类型、可信度、引用完整性。

按查询形态规划：

- **深度优先**：列出 3–5 条方法论或视角，说明每条视角如何回答核心问题、如何综合。
- **广度优先**：枚举互不重叠的独立子问题，按重要性与研究复杂度排序，必要时分批。
- **直接型**：确定最短的答案路径、必须核实的数据点、最相关的权威来源。

**开源方案门槛**：问题涉及软件、工具、自动化、实现、集成或部署时，检索前先读 `references/open-source-solutions.md`，把代码托管平台检索列为必做分支。

**产出**：`研究计划.md`，内容包括查询形态与验证强度、子任务拆分与边界、每个子代理的目标与预期产出、微信公众号检索安排、综合各路线发现的方法。

## 阶段三：RETRIEVE 并行检索

**目标**：系统收集多源信息，并当场把来源与证据落盘。

### 3.1 检索前准备

- 当前日期以运行时上下文为准，不要从训练数据推断年份；所有「近 12–18 个月」类查询都以该日期为基准。
- 把研究问题拆成 5–10 个独立检索角度：核心概念、技术细节、近期进展、学术来源、替代观点、统计数据、行业分析、局限与失败模式。

### 3.2 并行执行

1. 把所有相互独立的 `web_search` 调用放在同一条消息中并行发起；搜索结果返回后，用 `web_fetch` 抓取最有希望的来源全文。
2. 需要多步深挖的专题（学术论文、技术文档、代码仓库、专业领域）用 `subagent` 派子代理处理。子代理任务必须自包含，按 `references/expert-brief.md` 编写；多个 `subagent` 调用同消息并行发起。
3. 要求子代理返回结构化证据，而不是自由文本：

```json
{"claim": "具体论点", "evidence_quote": "来源原文", "source_url": "https://...", "source_title": "...", "confidence": 0.85}
```

### 3.3 证据即时落盘

每批检索完成后立即登记来源并写入证据，不要只留在对话上下文：

```powershell
> 推荐：把 JSON 对象写入 UTF-8 文件后使用 --json-file（PowerShell 下最稳）
python scripts\citation_manager.py register-source --json-file "来源1.json" --dir "research\<主题>_研究_<YYYYMMDD>"
python scripts\evidence_store.py add --json-file "证据1.json" --dir "research\<主题>_研究_<YYYYMMDD>"
```

来源写入 `来源.jsonl`，证据写入 `证据.jsonl`。稳定 `source_id` 用于跨轮次、跨代理复用；完整字段见 `references/evidence-chain.md`。

### 3.4 停止条件与来源质量

达到以下任一条件即停止扩大检索，进入阶段四：

| 验证强度 | 来源预算 | 平均可信度 | 兜底条件 |
| --- | --- | --- | --- |
| standard | 10–15 个来源 | > 60 分 | 边际收益明显递减 |
| deep | 20–30 个来源 | > 70 分 | 边际收益明显递减 |

来源多样性要求：

- 至少 3 种来源类型（学术、行业、新闻、技术文档、政府/机构）。
- 时间上混合近期来源与基础性旧来源。
- 观点上同时覆盖支持者、批评者与中性分析。
- 地域上不要只依赖单一国家来源。

可信度处理：按**定性筛选**判断来源——优先一手、官方、学术与具名机构来源；对营销稿、匿名聚合站、明显利益相关方保持警惕，并在报告中说明其对结论的影响。不做自动评分，也不设分数门槛（评分类工具已移除）。

**产出**：`来源.jsonl`、`证据.jsonl`，以及一份覆盖清单（哪些子问题已覆盖、哪些仍有缺口）。

## 阶段四：TRIANGULATE 三角验证

**目标**：用多个独立来源验证关键信息，形成可信事实基础。

**活动**：

1. 列出需要验证的论点，尤其是数字、日期、价格、法规、规格和直接引语。
2. 为每个关键论点寻找独立来源簇；同一通稿的转载、同一机构的重复发布只算一个来源簇。
3. 标记矛盾与不确定项，记录不同来源的说法与取舍理由。
4. 评估来源可信度、时效性与潜在利益倾向。
5. 区分共识区与争议区，逐条记录验证状态。

**质量门槛**：

- 每条主要结论至少 **2 个独立来源簇（standard）/ 3 个（deep）**。
- 单一来源支撑的信息必须显式标注。
- 过时信息要注明时间范围；无法调和的分歧写入报告的「局限」一节。
- 可用 `scripts/verify_claim_support.py` 校验论点与证据的对应关系。

**产出**：带置信度与验证状态的证据链。

## 阶段 4.5：OUTLINE REFINEMENT 提纲动态重构（仅 deep）

**目标**：根据检索到的证据调整报告结构，避免被初始提纲锁死。

**执行时机**：阶段四完成后、阶段五开始前。

**活动**：

1. 对照阶段一的范围与阶段三、四的发现，找出意外模式、矛盾与关键的新角度。
2. 判断是否需要调整提纲。出现以下任一信号就调整：主要发现推翻初始假设；证据显示存在比原计划更重要的角度；出现原计划未覆盖的关键子主题；原始问题过宽或过窄；多数来源都在讨论提纲之外的方面。
3. 调整方式：新增有证据支撑的章节；降级或删除证据不足的章节；按证据强度重排顺序；修正范围边界。
4. 重大缺口用 2–3 次定向检索补齐，只做快速补充，不重跑完整检索；时间控制在 2–5 分钟。
5. 在 `运行清单.json` 或报告的方法附录中记录调整内容与证据依据。

**约束**：

- 调整必须由证据驱动，不能凭「这样写更有趣」。
- 新增章节必须有已经收集到的证据支撑。
- 结构调整不超过原提纲的 50%；超过说明初始范围有严重问题，应回到阶段一重定范围。
- 保留原始研究问题的核心，不得整体漂移到另一个题目。

**产出**：反映真实证据格局的修订提纲。

## 阶段五：SYNTHESIZE 综合与洞察

**目标**：连接各来源的发现，生成超出单条来源的分析。

**活动**：

1. 识别跨来源的模式、趋势与反例。
2. 梳理概念之间的关系与因果链条。
3. 在来源事实之上提出有依据的洞察，并明确标注哪些是分析、哪些是推测。
4. 建立分析框架或论证结构，排列证据层级。
5. 检查每个论点是否能回到 `证据.jsonl` 中的具体证据。

**产出**：论点清单、论证结构与报告提纲。

## 阶段六：CRITIQUE 质量审查

**目标**：在交付前发现逻辑、证据与表达问题。

**常规审查（所有路径）**：

1. 检查逻辑一致性：论点之间是否冲突，结论是否由证据推出。
2. 检查引用完整性：每个关键事实是否有对应的 `[N]` 引用与证据记录。
3. 找出证据缺口、薄弱环节与未覆盖的反面观点。
4. 检查平衡性与客观性，避免把推测写成事实。
5. 用替代解释检验主要结论。

**红队问题**：还缺什么？哪里可能错？有哪些替代解释？可能存在什么偏差？需要考虑哪些反事实？

**多角色红队（仅 deep）**：模拟 2–3 个与主题相关的批评者角色：

- **怀疑的实践者**：日常做这件事的人会相信这些结论吗？
- **对抗性审稿人**：同行评审最可能拒掉哪一点？
- **实施工程师**：这些建议真的能落地执行吗？

**批判回环**：如果审查发现关键知识缺口（不是文字问题），带着定向「补差查询」回到阶段三补证，时间控制在 3–5 分钟，再进入阶段七。

**产出**：问题清单与修改建议。

## 阶段七：REFINE 迭代补强

**目标**：逐项修复阶段六发现的问题。

**活动**：

1. 针对证据缺口做补充检索，优先补关键事实。
2. 强化薄弱论证，删除证据不足的断言。
3. 补充缺失的视角与反面证据。
4. 解决或如实说明矛盾。
5. 提升表达清晰度，压缩空话。
6. 修改后重新核对引用与证据。

**产出**：修订后的报告内容与已关闭的问题清单。

## 阶段八：PACKAGE 交付

**目标**：产出可交付、可审计的中文研究报告。

**活动**：

1. 按 `references/report-template.md` 组织报告结构：标题、执行摘要、引言（研究问题、范围与方法、关键假设）、决策指南（条件）、主要发现、开源方案全景（条件）、分析综合、局限与说明、建议、参考文献、方法论附录。
2. 撰写执行摘要（200–400 字），确保可独立成立。
3. 正文以段落为主，少用项目符号；只有用户明确要求列表/排名或结构化对比时才用表格。
4. 编排参考文献：编号列表，每条 `[标题](URL)`，只列真实访问过的来源。
5. 适用时附方法与验证说明，写明检索范围、来源构成与主要局限。

**交付前校验**（完整清单以 `references/quality-gates.md:37-45` 为准）：

```powershell
python scripts\extract_claims.py extract --report "research\<主题>_研究_<YYYYMMDD>\研究报告.md" --dir "research\<主题>_研究_<YYYYMMDD>"
python scripts\citation_manager.py link-claims --dir "research\<主题>_研究_<YYYYMMDD>"
python scripts\verify_claim_support.py verify --dir "research\<主题>_研究_<YYYYMMDD>" --profile standard --strict
python scripts\validate_report.py --report "research\<主题>_研究_<YYYYMMDD>\研究报告.md" --profile standard
python scripts\verify_citations.py --report "research\<主题>_研究_<YYYYMMDD>\研究报告.md" --strict
```

`--profile` 按实际路径取 `direct` / `standard` / `deep`，`validate_report.py` 需与 `verify_claim_support.py` 使用同一档位。

适用时再运行 `validate_decision_guide.py` 与 `validate_open_source_solutions.py`。校验失败按 `references/quality-gates.md` 修复后重跑，最多 3 轮。**通过后运行 `citation_manager.py finalize-run --dir "[run目录]"`。**

**产出**：`研究报告.md`、`论点.jsonl`、更新后的 `运行清单.json`；需要网页版时按 `references/html-generation.md` 生成 `报告.html`。

## 工具映射

本技能的全部检索、深挖与脚本执行都在 DSH 内完成：网页检索用 `web_search` / `web_fetch`，并行深挖用 `subagent`，本地脚本与校验用 `pwsh`，不依赖任何平台专属工具。

| 研究动作 | DSH 工具 | 说明 |
| --- | --- | --- |
| 向用户澄清范围 | `ask_user_question` | 最多 3 问，必须用工具提问 |
| 加载中文检索技能 | `skill` | 优先加载 `wechat-article-search` |
| 网页搜索 | `web_search` | 多查询同消息并行发起 |
| 网页全文抓取 | `web_fetch` | 抓取搜索结果中最有价值的 URL |
| 并行深挖 | `subagent` | 异步、自包含简报、同消息并行 |
| 读计划与参考 | `read` | 按 `offset` / `limit` 分段读长文件 |
| 写计划与报告 | `write` / `edit` | 只写当前工作目录 |
| 运行脚本与校验 | `pwsh` | 调用 DSH 自带 Python，中文路径加引号 |
