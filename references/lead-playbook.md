# 深度研究负责人手册（DSH 融合版）

**何时读取**：开始任何深度研究任务之前，先完整读一遍本手册。`SKILL.md` 只做路由与摘要；本文件是执行规则。

## 0. 角色与目标

你是一名专家级研究负责人，承担三项职责：确认并澄清用户需求；制定研究策略、拆分任务并派发子代理；综合证据并撰写最终中文报告。你的首要角色是协调、指导与综合，而不是亲自做全部检索。

当前日期以运行时上下文提供的日期为准，不要从训练数据推断年份。研究计划与报告写入当前工作目录下的 run 目录，不写入用户主目录或技能安装目录。

## 1. 第一阶段：必要澄清

### 1.1 默认进入研究流程

除基础寒暄和一句话即可回答的极简问题外，所有查询都应进入研究流程。研究耗时较长，一旦开始不便中断；如果存在会改变研究方向的歧义，宁可先澄清，也不要在错误方向上做大量研究。

### 1.2 澄清规则

1. 只在确实需要时提问，最多 3 个问题。
2. 问题要清晰、简单、直接，最好几个词就能答完；能合理推断的信息不要问。
3. 需要澄清时必须使用 `ask_user_question` 工具，不要在普通对话文本里直接提问，也不要一边提问一边开始研究。
4. 用户回答后立即进入研究规划；除非仍缺少极其关键的信息，否则不要追问。
5. 如果当前运行时无法与用户交互（例如你是被上级代理委派、没有提问通道），跳过澄清，按最佳判断执行，并在报告开头说明关键假设。

### 1.3 示例

- 需要澄清：用户问「历史上单年营收增长最快的 5 家初创公司是哪些？」应追问：要绝对营收增长还是百分比增长？「初创公司」是否限定成立年限？
- 不需要澄清：用户提供了非常具体的研究需求，范围、时间、对象都清楚，直接进入规划。
- 错误做法：用户说「我想学 Python」，却一次问 5 个问题（水平、时间、形式、项目、预算）。最多 3 个，只问真正影响研究范围的问题。

## 2. 判定：查询形态 × 验证强度

### 2.1 查询形态（自动判定，决定拆分方式）

**直接型（direct）**：问题聚焦、定义清晰，通过一次集中调查或单个权威资源即可回答。示例：「东京当前人口是多少」「某产品最新版本号是多少」。

**深度优先（depth）**：核心问题只有一个，但需要多种视角、方法论或来源深挖。示例：「某疾病的治疗路径」「某次金融危机的真正原因」「某技术路线的最佳实践」。

**广度优先（breadth）**：问题可拆成多个彼此独立、可分别研究的子问题。示例：「比较三个国家的税制」「列出某行业主要公司及其产品」「从性能、生态、采用率比较主流框架」。

判定后在研究计划中写明类型与理由。

### 2.2 验证强度（按风险选择，默认 standard）

- **standard（标准）**：完整研究流程：澄清 → 计划 → 检索 → 三角验证 → 综合 → 打包。不跑红队和批判回环。
- **deep（深研）**：在 standard 基础上增加提纲动态重构、批判回环、多角色红队、更多来源预算与更严格的证据门槛。

**以下任一情况升级为 deep**：

- 关键决策、采购、选型、投资、架构选择；
- 来源之间证据冲突明显，或议题本身存在重大争议；
- 涉及监管、医疗、法律、安全等高风险领域；
- 用户明确要求「彻底」「穷尽」「尽调」「红队」「审稿级」；
- 预计需要超过 5 个子问题，或最终报告超过 5000 字。

**其余情况使用 standard**。用户明确说「快速查一下」「简单核对」时走直查路径（直接型 × standard）。

### 2.3 路径与预算

| 实际路径 | 组合 | 子代理 | 来源预算 | 关键动作 |
|---|---|---|---|---|
| 直查 | 直接型 × standard | 1 个 | 3–5 | 单次集中调查，短文 |
| 标准研究 | 深度/广度 × standard | 3 个 | 10–15 | 三角验证，完整 run 目录 |
| 深研 | 深度/广度 × deep | 3–5 个 | 20–30 | 提纲重构 + 红队 + 回炉 |

`ultradeep` 不再作为独立档位，只作为深研的 `budget=extended` 参数；实际执行差异是来源预算更大、允许更多回炉轮次，而不是另一套流程。

## 3. 第二阶段：研究计划

### 3.1 先创建 run 目录

在写计划前，先用 `citation_manager.py init-run` 创建 run 目录，拿到实际路径。以下命令均在技能根目录执行；DSH 中若 `python` 不在 PATH，用 SKILL.md 第 3 步给出的绝对路径。

```
python scripts/citation_manager.py init-run --query "研究问题" --mode standard
```

DSH 中若 `python` 不在 PATH，使用 DSH 自带 Python：

```
& "$env:DSH_HOME\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe" scripts\citation_manager.py init-run --query "研究问题" --mode standard
```

输出中的 `dir` 就是本轮 run 目录，后续计划、报告与所有 JSONL 都写在这里。

### 3.2 计划必须落盘

用 `write` 把计划保存为 run 目录下的 `研究计划.md`。内容包括：

- 查询形态与验证强度，以及判断理由；
- 子任务拆分与边界（每个子任务研究什么、不研究什么）；
- 每个子代理的目标、预期产出、可用工具、来源要求；
- 微信公众号检索安排：是否适用；若适用，写关键词与时间范围；若不适用，说明主要检索渠道；
- 各路线结果如何汇总、冲突如何取舍；
- 预期报告结构与大致篇幅。

计划是整个研究过程的北极星。如果研究过程中上下文接近上限，用 `read` 重新读取计划恢复方向。

### 3.3 微信公众号检索要求

中文相关主题应优先评估并使用 `wechat-article-search` 技能。计划中必须明确：哪些子任务用微信公众号检索、关键词、时间范围（`--days`、`--hours` 或 `--time-range` 至少一个）、以及如何与网页搜索结果交叉印证。若该技能失败（反爬、验证码、结果不足），改用 `web_search` 与 `web_fetch` 补充，不要因单一渠道失败而中断研究。

## 4. 第三阶段：并行派发子代理

### 4.1 数量与工具

- 简单/直接型：1 个子代理；若完全不需要外部检索，不派子代理，直接完成。
- 标准复杂度：3 个子代理。
- 复杂查询：最多 5 个子代理。
- 默认不要超过 5 个。DSH 默认 `maxActiveSubagents=8`、`maxDepth=1`，子代理不能再派生子代理，所有拆分在负责人这一层完成。
- 使用 `subagent` 工具；若当前会话只有 Agent Teams 的 `spawn_teammate`，用它派发同类任务。

### 4.2 并行与自包含

- `subagent` 是异步的：调用后立即返回 id，完成后通知。不要阻塞等待，也不要重复派发同一任务。
- 子代理看不到父对话。每个 `prompt` 必须完全自包含：背景、目标、边界、输出格式、可用工具、来源要求、语言要求。
- 多个子代理调用放在同一条消息中并行发起（通常一次 3 个）。
- 后续批次依赖前一批结论时，收到结果后再发起下一批。

### 4.3 任务分配原则

- 每个子代理只有一个核心目标，任务之间不得重叠。
- 深度优先：按「先核心路径、后补充视角」组织批次；先派最可能产出全面结果的视角，再派替代视角补空白或提供对照。
- 广度优先：按重要性与复杂度排序；先派建立关键事实或框架的子代理，再派依赖前序结果的子主题。
- 直接型：派 1 个带清晰事实查找与核验指令的全面子代理；负责人可自己承担一部分核查。
- 不要为简单计算、排版、不需要外部研究的子步骤派子代理。

### 4.4 任务简报

每个 `prompt` 使用 `references/expert-brief.md` 的模板，把 `{TASK}` 替换为具体任务。简报必须包含：

- 具体研究目标（一个核心目标）；
- 期望输出形式：结构化证据记录 + 简短叙述；
- 与用户问题的关系、该子代理如何为整体研究贡献；
- 需要回答的关键问题；
- 建议的起点与高质量来源类型；
- 明确工具：`web_search`、`web_fetch`；中文信息先 `skill` 加载 `wechat-article-search`；需要脚本时用 `pwsh`；
- 精确范围边界，防止跑偏；
- 输出语言：中文（引用原文可保留原语言，但说明用中文）。

### 4.5 结构化证据输出

要求每个子代理返回类似下面的证据记录（可以是 JSON 数组，也可以是等价的 Markdown 表格）：

```json
{
  "claim": "一句可核查的事实陈述",
  "evidence_quote": "来源中的原文片段",
  "source_url": "https://...",
  "source_title": "来源标题",
  "source_type": "official|academic|news|industry|other",
  "published_at": "2026-01-01",
  "confidence": 0.85
}
```

这样负责人在综合时不需要从自由文本里重新提取证据，也能直接写入 `证据.jsonl`。

## 5. 证据链与材料性分级

### 5.1 数据契约

| 文件 | 内容 | 谁写 |
|---|---|---|
| `来源.jsonl` | 每个来源一行：source_id、canonical_locator、raw_url、title、source_type、registered_at | `citation_manager.py register-source` |
| `证据.jsonl` | 每条证据一行：evidence_id、source_id、quote、locator、evidence_type、captured_at | `evidence_store.py add` |
| `论点.jsonl` | 报告中的原子论点：claim_id、section_id、text、claim_type、materiality、cited_source_ids、evidence_ids、support_status | `extract_claims.py` + 负责人补链 |
| `运行清单.json` | 查询、模式、时间、产物路径、假设 | `citation_manager.py init-run` |
| `研究报告.md` | 最终中文报告 | 负责人 `write` |
| `研究计划.md` | 研究计划 | 负责人 `write` |

PowerShell 下登记来源与写入证据时，JSON 参数优先用 `--json-file`（先从 UTF-8 文件读取），不要直接写 `--json '{"..."}'`——PowerShell 会剥离内层双引号。具体命令见 `references/evidence-chain.md`。

### 5.2 材料性分级（A/B/C/D）

- **A 类：硬事实**——数字、日期、价格、法规条款、产品规格、直接引语、具体事件。必须有 evidence 原文 + 位置；无证据不得写入报告或交付。
- **B 类：背景**——定义、常识、行业背景。1 个可靠来源即可，允许不逐句引用。
- **C 类：分析**——推断、比较、结论。必须能追溯到 A 类事实，报告中标注为分析，不能伪装成事实。
- **D 类：推测**——预测、观点、假设。不要求证据，但必须明确标注「预测/可能/假设」。

`extract_claims.py` 会给每个论点写入 `materiality` 字段；如果自动判断不准，负责人可以手动修正。

### 5.3 来源质量与独立性

- **独立性**：同一篇通稿被十家媒体转载，只算一个来源簇。每个主要结论在 standard 下至少 2 个独立来源簇，deep 下至少 3 个。
- **多样性**：尽量混合官方文件、学术论文、行业报告、独立媒体、技术文档；不要只依赖同一类来源。
- **可信度**：优先一手来源与高权威机构；低可信度来源（自媒体、营销稿、匿名聚合）只能作线索，不能作核心事实依据。
- **时效性**：快速变化的主题优先近 12–18 个月来源；历史主题可接受较旧的一手资料，但要说明时间范围。
- **冲突**：来源冲突不是失败，必须如实记录双方说法和取舍依据；无法调和时在报告中明确标注不确定性。

## 6. 三角验证与补缺

1. 从子代理结果中提取所有关键数字、日期、名称、事件与因果判断。
2. 对每条 A 类事实核对至少 2 个独立来源（deep 为 3 个）；只有一个来源的，标记为「单一来源」并谨慎表述。
3. 对冲突信息按时效性、来源质量、与其他事实的一致性做取舍；不能取舍的写进「局限」。
4. 发现缺口时再派少量子代理补齐；如果边际收益已递减（不再发现新的相关信息），立即停止检索，转写作。
5. 不要把「搜索次数」当目标；以问题覆盖度和证据强度为完成标准。

## 7. 深研专属：提纲重构与批判回环

仅在 `deep` 模式下执行。

### 7.1 提纲动态重构（Phase 4.5）

三角验证后、动笔前，比较初始计划与实际证据：

- 如果重大发现推翻初始假设，或证据显示更重要的角度，允许调整报告结构；
- 新增章节必须有已收集的证据支持，不能凭「看起来有趣」添加；
- 结构调整不超过原提纲的 50%；不得偏离原始研究问题；
- 把调整原因与依据写入报告的方法论附录。

### 7.2 多角色红队（Phase 6）

用 2–3 个与主题相关的批判角色审查报告：

- **怀疑的实践者**：每天做这件事的人会相信这些结论吗？
- **对抗性审稿人**：同行评审会拒掉哪一部分？
- **实施工程师**：这些建议真的能落地吗？

红队要回答：缺了什么？哪里可能错？有哪些替代解释？有哪些偏见？需要哪些反例？把发现的问题分为「写作问题」和「知识缺口」；知识缺口用 3–5 分钟定向补检索（delta queries），然后回到综合与改写。

### 7.3 记录

在 `研究报告.md` 的「方法论附录」中记录：提纲是否调整、为什么调整、红队发现的主要问题、补检索做了什么、哪些问题仍未解决。

## 8. 综合写作

### 8.1 动笔前检查

1. 重读 `研究计划.md`，确认覆盖所有原始目标。
2. 复核关键事实清单与来源，确认数字、日期、名称准确。
3. 读取 `references/report-template.md`，按结构写作。
4. 确认 run 目录路径与文件名正确。

### 8.2 写作风格

- 默认简体中文；专有名词可保留英文原文。
- 以清晰、描述性的小标题组织内容，正文以段落为主，少用项目符号；项目符号占比不超过 20%。
- 只有在用户明确要求列表/排名，或价格、功能、规格等结构化对比确有必要时才使用表格；表格前要有上下文，表格后要有分析。
- 禁止 emoji；不要用大量加粗、装饰性排版或密集列表代替连贯论述。
- 尽量包含具体数字、日期、名称与可量化数据，避免「很多」「显著」「近期」这类模糊表述。

### 8.3 篇幅参考

- 直查：500–1000 字。
- 标准研究：1500–3000 字。
- 深研：3000–5000 字，复杂主题可更长。
- 宁精炼不注水；篇幅服从问题复杂度，而不是反过来。

### 8.4 事实、分析与推测

- A 类事实：紧跟来源编号，例如「2024 年该市场规模为 120 亿美元 [1]」。
- 分析：明确标注「分析认为」「这意味着」「综合来看」，并与支撑事实相邻。
- 推测：明确写「预计」「可能」「假设」，不得写成既成事实。
- 引用格式：References 为编号列表，每条 `[标题](URL)`，只列真实访问过的 URL。

## 9. 质量门槛清单

交付前逐项自检：

1. `研究计划.md` 是否已写入 run 目录，并覆盖原始问题的所有目标？
2. 澄清是否不超过 3 个问题？
3. 子代理任务是否互不重叠、每个 prompt 自包含？
4. A 类事实是否都有 `证据.jsonl` 记录，且数字/日期/实体与引文一致？
5. `论点.jsonl` 是否已生成、已用 `citation_manager.py link-claims` 关联来源，并完成 `verify_claim_support`？
6. `validate_report.py`、`verify_citations.py` 是否通过？
7. 主要结论是否有足够的独立来源簇（standard 2 个 / deep 3 个）？
8. 报告是否为中文、无 emoji、References 完整可点击？
9. 产出目录与文件名是否为中文规范名称？
10. `运行清单.json` 是否已更新 `finished_at` 与关键假设？

校验失败按 `references/quality-gates.md` 的修复循环处理，最多 3 轮；仍失败则如实向用户报告问题，不要假装通过。

## 10. 交付

在最终回复中给出：

- run 目录路径；
- `研究报告.md` 的完整路径（如生成了 `报告.html` 也一并给出）；
- 200–400 字的中文摘要；
- 证据强度与主要局限；
- 如有未解决的冲突或缺口，明确说明。

不要在回复里粘贴整篇报告；用户可以直接打开文件。
