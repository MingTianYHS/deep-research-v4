# 报告组装：渐进式写作流程

**何时读取**：报告预计超过 8000 字，或需要分节写入、多人协作续写、控制单次输出长度时读取。

**用途**：规定 run 目录与中文文件命名、逐节生成与落盘的顺序、每节字数控制、引用登记方式，以及组装完成后的检查项。

## 1. 篇幅与触发条件

篇幅按 `references/report-template.md` 执行：直查 500–1000 字；标准研究 1500–3000 字；深研 3000–5000 字（复杂主题可延长）。所有路径都按本节规则分节写入。

- 全文不超过 8000 字：先完成研究与提纲，再**按节分批写入（每节一次，通常 3–5 次）**，不要试图一次性写完。
- 全文 8000–18000 字：必须使用渐进式写作，每节单独写入。
- 全文超过 18000 字：在渐进式写作基础上启用 `references/continuation.md` 的续写协议。

**单次写入硬限制**：任何一次 `write` / `edit` 调用不超过 2000 字。宁可多分几节，也不要一次塞入长文。

## 2. run 目录与文件命名

run 目录统一为 `research/<主题>_研究_<YYYYMMDD>/`（Windows 实际路径写作 `research\<主题>_研究_<YYYYMMDD>\`）。先用 `citation_manager.py` 解析并创建，不要手工拼目录名：

```powershell
$skill = "<DSH 技能根目录>\deep-research"
python "$skill\scripts\citation_manager.py" init-run --query "研究问题" --mode <direct|standard|deep> --out-dir "<工作目录>\research\<主题>_研究_<YYYYMMDD>"
```

直查用 `direct`，标准研究用 `standard`，深研用 `deep`；深研需要更大预算时追加 `--budget extended`。查询形态为广度优先时加 `--query-type breadth`（默认 `depth`）。**始终以用户工作目录为 cwd，用 `--out-dir` 显式指定 run 目录**，避免产物落进技能安装目录。

脚本返回的 `dir` 就是本轮 run 目录（通常为当前工作目录下的绝对路径）。后续所有脚本调用都原样使用该路径；主题清洗、中文「研究」后缀、日期与重名后缀 `_2` / `_3` 都由脚本负责。

run 目录内统一使用以下中文文件名：

| 文件 | 用途 |
| --- | --- |
| `研究报告.md` | 最终 Markdown 报告 |
| `研究计划.md` | 研究计划与范围、子任务边界 |
| `来源.jsonl` | 来源登记表，一行一个来源 |
| `证据.jsonl` | 证据表，一行一条原文证据 |
| `论点.jsonl` | 从报告抽取的论点与证据对应关系 |
| `运行清单.json` | run 元数据、产物路径、进度与校验记录 |
| `开源方案.jsonl` | 适用时的开源方案核验记录 |
| `报告.html` | 可选，HTML 版报告 |

所有产物放在同一个 run 目录内，不要复制到全局目录或第二个位置；续写代理与校验脚本都从报告所在目录解析产物。

## 3. 写作前准备

1. 用 `read` 读取 `研究计划.md`，确认原始问题、范围、子任务与预期产出。
2. 复核 `证据.jsonl` 与论点草稿，确认关键结论都有证据；缺口先补，不要边写边猜。
3. 按查询形态确定报告结构，列出章节清单与每节目标字数。
4. 对照 `references/report-template.md` 检查结构是否覆盖：执行摘要、引言（研究问题、范围与方法、关键假设）、决策指南（条件）、主要发现、开源方案全景（条件）、分析综合、结论、局限与说明、建议、参考文献、方法论附录。

## 4. 分节生成流程

### 4.1 初始化产物

`init-run` 会创建 `运行清单.json` 与空的 `来源.jsonl`、`证据.jsonl`、`论点.jsonl`。若研究涉及软件、工具、自动化、实现或集成，还要按 `references/open-source-solutions.md` 创建 `开源方案.jsonl`。

### 4.2 随检索登记来源

每遇到一个新来源就登记，不要等写报告时补：

```powershell
> 推荐：把 JSON 对象写入 UTF-8 文件后使用 --json-file
python scripts\citation_manager.py register-source --json-file "来源1.json" --dir "research\<主题>_研究_<YYYYMMDD>"
```

脚本返回稳定的 `source_id`（基于哈希，续写和重排后不变）。正文中的显示编号在全部来源登记完成后统一生成：

```powershell
python scripts\citation_manager.py assign-display-numbers --dir "research\<主题>_研究_<YYYYMMDD>"
```

显示编号只是渲染结果，不写回来源记录；这样上下文压缩或续写后仍能按 `source_id` 恢复引用关系。

### 4.3 逐节写入

每次 `write` / `edit` 只处理一节，写完立刻落盘，再进入下一节。推荐顺序：

1. **标题与执行摘要**（200–400 字）：用 `write` 创建 `研究报告.md`，写标题与执行摘要。摘要必须独立成立，只读摘要也能抓住核心答案；不要写「本文将……」。
2. **引言**（400–800 字）：写研究问题、范围与方法、关键假设，说明研究背景与问题重要性。用 `edit` 追加。
3. **分支决策指南**（条件章节，对比、选型、采购、架构选择、采纳类报告必写）：放在引言之后、详细发现之前。先写会改变答案的硬门槛，再写分支路径与终端建议，最后在 `### 选择结果` 小节用文字重复所有终端结论。写完运行 `python scripts\validate_decision_guide.py --report "research\<主题>_研究_<YYYYMMDD>\研究报告.md" --strict`。
4. **发现 1–N**（每节 600–2000 字）：按逻辑分节，每节围绕一个可检验的判断展开；具体数字、日期、名称写在句子里，并紧跟 `[N]` 引用。用 `edit` 逐节追加。
5. **开源方案全景**（条件章节，软件/工具/自动化/实现类报告必写）：基于 `开源方案.jsonl` 写对比表与文字分析，给出 canonical 仓库直链，区分仓库事实与采纳建议；完成后按 `references/open-source-solutions.md` 运行 `validate_open_source_solutions.py --strict`。
6. **分析综合**：比较不同视角、识别模式与矛盾，说明证据强弱；不要把前文事实简单复述一遍。
7. **结论**：直接回答原始问题，不引入正文没有支持的新事实。
8. **局限与说明**：说明数据、时间范围、来源可得性、方法限制与后续研究方向。
9. **建议**：给出可执行动作、优先级与前置条件；没有把握的建议要标注不确定性。
10. **参考文献**：列出正文用到的每一个编号来源，不得缺号、不得写区间、不得截断。每条使用 `[标题](URL)`。
11. **方法论附录**：检索范围、来源构成、验证方式、提纲调整与红队发现、主要取舍。

### 4.4 每节完成检查

- 该节是否回答了一个明确问题，而不是堆砌背景。
- 关键事实是否都有 `[N]` 引用，并且 `证据.jsonl` 中存在对应证据。
- 数字、日期、名称是否具体；是否存在「很多」「显著」「近期」这类模糊表述。
- 段落是否为主，项目符号是否只用于真正的并列清单。
- 字数是否接近计划，单次写入是否低于 2000 字。

## 5. 文件组织与交付

- 所有文件都在 `research\<主题>_研究_<YYYYMMDD>\` 这一个目录内。
- 报告正文只写 `研究报告.md`；HTML 版另存为同目录 `报告.html`。
- 交付前运行 `extract_claims.py` 生成 `论点.jsonl`，运行 `citation_manager.py link-claims` 关联来源，再运行 `verify_claim_support.py`、`validate_report.py`、`verify_citations.py`。
- `运行清单.json` 记录最终产物路径、查询形态、验证强度、语言与完成时间；不要留空字段或模板占位符。

## 6. 常见错误

- 先写报告后补来源，导致引用编号与来源表对不上。
- 把多个章节塞进一次 `write`，触发输出截断或留下半截段落。
- 用 `[1-10]`、`[略]`、`TBD` 等占位内容充当参考文献。
- 在 run 目录外另存一份报告，造成校验对象不明确。
- 报告改完后没有重新生成 `论点.jsonl`，导致论点校验基于旧版本。
